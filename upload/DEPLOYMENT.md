# BrandBox: просмотр, публикация и заявки

## Что доступно сейчас

Пользователь опубликовал статическую версию через Cloudflare Pages: https://brandbox.pages.dev/. Исходники — GitHub AMF-marketing/BrandBox, ветка main; сборка npm run build, выходная папка out. Новые коммиты запускают автоматическую сборку. SEO-обновление от 20.10.2026 подготовлено локально: инструкция загрузки в SEO-UPDATE.md. Реальные заявки не подключены.

Браузерная политика запретила localhost. Другой браузер, прокси или отключение защиты не применялись. Скриншоты и визуальный QA отсутствуют.

## Открыть на вашем компьютере

PowerShell в папке проекта:

```powershell
./START.ps1
```

Открыть http://127.0.0.1:3001/. Для другого порта: `./START.ps1 -Port 3015`. Требуется только Node.js, зависимости для готового экспорта не нужны.

Разработка и новая статическая сборка:

```sh
npm ci
npm run dev
npm run typecheck
npm run build
```

`npm run dev` использует порт 3000. Статический режим остаётся демо и не содержит работающего API. Реальные заявки требуют отдельного серверного режима. Текущие пути рассчитаны на корень домена, не на `/repository/`.

## Приватный предпросмотр Vercel

1. Загрузить содержимое папки `brandbox` в приватный GitHub-репозиторий. Не загружать `.env.local`, `node_modules`, `.next` или секреты.
2. Создать/связать проект Vercel. Framework — Next.js, Root Directory — папка с `package.json`. Конфигурация `vercel.json` уже задаёт серверную сборку.
3. **До деплоя** включить подходящую Deployment Protection с Vercel Authentication и проверить, какие URL она защищает в вашем аккаунте/тарифе. Убедиться, что Preview закрыт для посторонних. Настройка `robots` не ограничивает доступ.
4. Для первого Preview оставить `NEXT_PUBLIC_ORDERS_ENABLED=false` и `ORDERS_ENABLED=false`. Создать только Preview deployment, без `--prod`. Проверить доступ из окна без авторизации: оно должно требовать вход, а не показывать сайт.
5. На защищённой ссылке проверить главную, каталог, товар, меню и форму при ширинах 320, 480, 768, 1024 и 1440. Выполнить проверку консоли, клавиатуры и Lighthouse.
6. Публичный production-деплой выполнять только после отдельного подтверждения заказчика и заполнения фактического контента.

Официально: [Vercel Deployment Protection](https://vercel.com/docs/deployment-protection). Эта инструкция не означает, что облачный деплой был выполнен или защита уже включена.

Для собственного Node.js-хостинга:

```sh
npm ci
npm run build:server
npm run start:server
```

Нужны TLS и контролируемый reverse proxy. Предпросмотр и реальное обслуживание персональных данных могут использовать разные среды; оператор должен согласовать инфраструктуру и получателей до включения заявок.

## Сервер заявок

Endpoint: `POST /api/orders/`, JSON, до 16 KB. Обработчик проверяет имя, телефон, категорию, способ связи, комментарий, два согласия и версию документа. Включение требует полного набора серверной конфигурации. Без него ответ 503, успех не имитируется.

Защита: точное совпадение Origin, honeypot, серверная проверка Turnstile с hostname/action, атомарный лимит 5 попыток за 10 минут в Redis REST, тайм-ауты и запрет redirect при серверных запросах. Секреты находятся только на сервере. Идентификатор IP в Redis — HMAC с отдельным секретом, TTL 10 минут. Заявки в Redis не сохраняются. Тело заявки и IP не пишутся приложением в журнал; отдельно настроить журналы и сроки хранения у хостинга и получателя.

Turnstile подключается только в live-интерфейсе. Токены одноразовые; после ошибки клиент получает новую проверку. [Серверная проверка Cloudflare](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/).

## Что настроить для настоящих заявок

Скопировать `.env.example` в `.env.local` для локального сервера либо добавить переменные в защищённые настройки хостинга. Пример не содержит секретов.

| Переменная | Нужные данные |
|---|---|
| `SITE_ORIGIN` | Точный HTTPS origin рабочей среды, без пути |
| `NEXT_PUBLIC_SITE_ORIGIN` | Тот же origin для canonical, sitemap и Open Graph |
| `ORDER_WEBHOOK_URL` | HTTPS адрес почтового шлюза/CRM-получателя |
| `ORDER_WEBHOOK_TOKEN` | Серверный секрет авторизации шлюза |
| `TURNSTILE_SECRET_KEY` | Серверный ключ Cloudflare |
| `NEXT_PUBLIC_TURNSTILE_SITE_KEY` | Публичный ключ виджета для согласованных доменов |
| `RATE_LIMIT_REDIS_URL`, `RATE_LIMIT_REDIS_TOKEN` | Redis REST endpoint и токен с EVAL/INCR/EXPIRE/TTL |
| `RATE_LIMIT_HASH_SECRET` | Случайный секрет не менее 32 байт, отдельно от остальных ключей |
| `ORDERS_CONSENT_VERSION`, `NEXT_PUBLIC_CONSENT_VERSION` | Одна утверждённая версия фактически опубликованных документов |
| `TRUST_PROXY` | `true` только за доверенным ingress, перезаписывающим X-Forwarded-For |
| `ORDERS_LEGAL_READY` | `true` после заполнения/утверждения политики, согласий, оператора и условий обработки |
| `ORDERS_ENABLED`, `NEXT_PUBLIC_ORDERS_ENABLED` | Оба `true` только после проверки получателя и всей конфигурации |

Публичные переменные встраиваются при сборке: после изменения пересобрать и передеплоить. Серверные секреты никогда не получают префикс `NEXT_PUBLIC_`.

Сборка live-интерфейса блокируется, если серверный режим, обязательные переменные, готовность юридических документов, origin и версия согласия не согласованы. Не включать live только ради предпросмотра: для оценки дизайна достаточно деморежима.

Почтовый вариант требует адреса получателя, подтверждённого отправителя/домена и серверных реквизитов провайдера **на стороне шлюза**. CRM-вариант требует endpoint, токен, соответствие полей и правил создания обращения. Оба используют одинаковый контракт ниже; готового подключённого получателя в проекте нет.

## Контракт получателя

Шлюз принимает JSON с именем, телефоном, выбранной продукцией, способом связи, комментарием, `dataConsent`, `marketingConsent`, `consentVersion`, `receivedAt`, `requestId`.

Заголовки: `Authorization: Bearer <secret>`, `Idempotency-Key: <requestId>`, `X-BrandBox-Signature: sha256=<HMAC body>`. Шлюз проверяет авторизацию/подпись и дедуплицирует запросы по ключу. Возвращает **только после сохранения заявки или подтверждённого принятия почтовым сервисом**:

```json
{"accepted":true,"id":"реальный-идентификатор-получателя"}
```

Это пример формата, не фиктивный endpoint. Ответ 200 без `accepted:true` и непустого реального ID считается ошибкой. Сохранение и повторы доставки обеспечивает получатель с долговечной очередью; функция Next.js не хранит заявки в своей временной файловой системе. Принятие почтовым сервисом не гарантирует попадание письма во входящие — для этого нужны события доставки и мониторинг на стороне шлюза.

## Финальный checklist

- Подтверждённый контент, цены, ассортимент, контакты, адрес и документы.
- Защищённый Preview доступен только разрешённым пользователям.
- Обычный браузер: страницы, фильтры, форма, клавиатура, адаптивность, консоль.
- End-to-end с вашим получателем: реальный ID, повтор без дубля, отказ получателя, тайм-аут, лимит попыток, недействительный токен, отзыв рекламного согласия.
- Условия хранения, доступ сотрудников и обработка обращений у оператора.
- Домен/canonical/OG и разрешение индексации после согласованного запуска.

Перед коммерческим деплоем проверить актуальные официальные advisories Next.js/React и зависимости (`npm audit`); этот проект не заявляется полностью проверенным аудитом безопасности инфраструктуры.

При выборе модели сервер добавляет catalogItem: slug, unitPrice, priceFrom, currency. Цена берётся из серверного каталога, а не из присланных клиентом данных. Для индивидуального запроса catalogItem = null. Шлюз должен принимать эти поля и учитывать, что priceFrom обозначает начальную стоимость.
